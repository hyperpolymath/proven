# JWT and SQL remediation: implementation and evidence

Date: 2026-11-16. Baseline: `c13619f9a67a1b9e8234e22e22dae0940d2480cb`.
Branch: `fix/critical-proof-remediation-20261116`.
Changes are local and uncommitted. No hosted CI run, push, PR, merge or release
was performed for these changes.

JWT's fabricated signing path is contained. SQL literal rendering and the
named-parameter raw-value bypass are repaired within the scope below.
Neither complete JWT functionality nor whole-query SQL injection freedom is
claimed. The prioritized plan remains `2026-11-16-plan.md`; the 374-row CSV
remains a baseline review inventory.

## JWT: explicit unavailability

`createToken` and `createHS256Token` no longer return placeholder-signed tokens.
`verifySignature` returns failure for every key and decoded token, including
`None`/`NoKey`. Algorithms other than `None` report `CryptoUnavailable alg`;
`None` reports `AlgorithmNoneNotAllowed`. Boolean verification helpers return
False. The four bodyless verification primitives and private fake signer/
incomplete serializers are removed.

Inspection and claims-only checks remain usable; they do not establish
authentication. The public `ValidatedJWT` constructor is not proof of
authentication, and the proofs concern actual validation API results.

In `src/Proven/SafeJWT/Containment.idr`, total proofs establish:

| Theorem | Proposition about production code |
| --- | --- |
| `creationNeverSucceeds` | For every header, claims, key and output, successful `createToken` equality implies Void. |
| `hs256CreationUnavailable` | Every `createHS256Token` call returns the specified HS256 unavailability error. |
| `signatureNeverVerified` | No key and decoded token can make `verifySignature` return Ok. |
| `validationNeverSucceeds` | No options, key, time, decoded token or result can make full `validate` succeed, even if claims checks pass. |
| `hmacUnavailable`, `rsaUnavailable`, `ecdsaUnavailable`, `eddsaUnavailable` | Every compatibility Boolean verifier returns False. |

These are real rejection/containment theorems, not implemented cryptographic
correctness. The existing compatibility implications in `SafeJWT.Proofs` have
impossible acceptance premises while the backend is absent; they are explicitly
identified as vacuous and are not reported as security proofs.

Still required before enabling authentication: faithful JSON/UTF-8/Base64URL
serialization, implemented MAC/signature backends, algorithm/key policy,
exact signed-byte contracts, standard vectors, tampering tests, relevant
claims proofs, and checks through the actual delivered native artifact.

## SQL: lexical contracts and raw parameters

`src/Proven/SafeSQL/Literal.idr` defines two explicit quote modes:
`StandardQuotes` and `BackslashEscapes`. Its structurally recursive
`encodeBody` produces both characters and a `BodyEncoding` witness indexed by
the actual input and output. The relation doubles apostrophes, doubles
backslashes only in backslash mode, retains ordinary full characters, and
explicitly models the legacy removal of NUL.

The production `renderBody` and `renderLiteral` consume this encoder.
`RenderedBody` and `RenderedLiteral` connect the character relation to the
actual packed String, including the outer delimiters for a full literal.
A separate `PairedQuotes` grammar is proved by induction over the encoding.
A lone body apostrophe has no witness.

| Theorem | Exact scope |
| --- | --- |
| `bodyCorrect`, `renderBodyCorrect`, `renderLiteralCorrect` | Actual production results satisfy the indexed encoding/representation relation. |
| `encodingQuotesPaired`, `singleQuoteNotPaired` | Encoded body quotes occur in pairs; a lone quote cannot inhabit that grammar. |
| `escapeStringQuotesSafe`, `escapedBodyQuotesPaired` | The dialect-default production renderer satisfies these lexical contracts. |
| `SafeString.Proofs.escapeSQLSafe` | The legacy body-only API returns the represented backslash-mode encoding. |
| `checkedLiteralCorrect` | A successful checked-rendering result has the corresponding literal witness. |
| `parameterValuesDoNotChangeSQL` | Replacing positional/named values cannot change the template emitted by `renderQuery`. This does not certify template provenance. |
| `strictParametersBound`, `rawHeadImpossible` | Actual strict-validation success excludes SQLRaw from the combined positional and named parameter lists; a raw head cannot have that evidence. |

`validateQueryStrict` now checks both parameter collections; previously named
SQLRaw values bypassed the rejection. Its remaining SQL text scanner is a
heuristic, explicitly labeled as such.

False quote-free witnesses and unsupported universal builder/composition/
injection-safety APIs are removed. Withdrawing those claims is not discharging
their intended obligations. Public Literal, SQLRaw and identifier constructors
still do not establish provenance. Driver binding, parser refinement and
whole-query safety remain open.

### Behavioral and compatibility changes

- JWT creation/authentication now fail rather than fabricate a success.
  `CryptoUnavailable` is a new public error variant. Unsigned tokens are not
  accepted as authentication, including under permissive options.
- SQL newline and carriage-return characters are preserved inside one literal.
  PostgreSQL standard strings preserve backslashes; MSSQL rendering no longer
  emits a concatenation of CHAR expressions.
- Default PostgreSQL rendering assumes `standard_conforming_strings=on`;
  default MySQL rendering assumes `NO_BACKSLASH_ESCAPES=off`. Callers with
  different settings must use the matching explicit quote mode.
- Legacy `escapeString` and body-only `escapeSQL` still remove NUL.
  `checkedEscapeString` rejects NUL instead. Legacy lossiness is not a
  data-preservation guarantee.
- The old SQL proof vocabulary changes incompatibly. In particular, callers
  relying on quote-free, unconditional injection-safety or RawTrusted evidence
  must migrate to the narrower indexed relations. The package builds with its
  in-repository callers; external consumers have not been tested.

The dialect assumptions follow the official
[SQLite literal syntax](https://www.sqlite.org/lang_expr.html),
[PostgreSQL lexical syntax](https://www.postgresql.org/docs/current/sql-syntax-lexical.html)
and [MySQL string-literal rules](https://dev.mysql.com/doc/refman/8.4/en/string-literals.html).
Only SQLite was executed as a database receiver here. Charset conversion,
connection settings, other dialects' complete semantics and actual parameter
binding are separate integration obligations.

## Executed validation

Toolchain: Idris 2 `0.8.0-b6cbc25d5` with Chez, Julia `1.13.1`, SQLite
`3.46.1`, Debian under WSL.

1. Fresh source-only staging via `scripts/test-critical-remediation.sh`:
   **PASS**, exit 0. Generic proof regressions and affected production modules
   type-check; **519 previous + 5,174 JWT/SQL runtime assertions** pass.
   The new cases cover all 14 algorithm tags, nine key forms, multiple claims
   and signature inputs, permissive validation, explicit errors, claims/expiry,
   inspection and the Idris exports. SQL includes all 400 strings of length
   zero to three over a seven-character alphabet, checked NUL policy and
   positional/named raw-parameter rejection.
2. Real in-memory SQLite: **405 exact-byte literal cases**, plus count and
   sentinel-preservation assertions, **PASS**. Expected UTF-8 bytes are
   independently specified. Cases include quote/slash combinations, CR/LF,
   NUL policy, comments, Unicode and an attempted DROP TABLE payload.
   Julia passes the generated bytes directly to
   [SQLite's C API](https://www.sqlite.org/c3ref/exec.html); no database mock is
   used. This is receiver testing of generated literals, not driver-binding
   validation or proof of every possible query.
3. **Five negative compilation fixtures rejected** for type/constructor
   mismatches: FalseGoal, ForgedWebhook, ForgedJWT, LoneSQLQuote and
   RawSQLParameter. Missing-import or syntax failures are not accepted as
   successful negative tests.
4. Baseline sensitivity: compile the baseline-compatible common cases against
   an archive of the unchanged baseline. **132 of 537 fail**, process exit 1,
   versus all passing on the repaired code. The separate first-batch baseline
   control remains **313 failures out of 519**. The new full verification matrix
   cannot be run meaningfully against bodyless baseline crypto primitives;
   the 537-case comparison deliberately uses executable baseline APIs.
5. Full `idris2 --build proven.ipkg`: **PASS**, exit 0, reaches **312/312**.
   This package build reuses this checkout's earlier generated cache. The
   focused proof/runtime run above independently stages only source files.
6. `git diff --check`: **PASS**.
7. SQLite harness controls: exact CRLF input passes through the C API; the same
   SQL fails its byte assertion through the line-processing CLI. A deliberately
   false CHECK also makes the Julia harness fail. The original failing
   receiver case was retained when switching the transport to the raw API.

## Native bridge: unresolved source, not confirmed private

The checked workflow expects `nextgen-languages/language-bridges` and a checkout
at `nextgen-languages/language-bridges` within proven. Zig resolves the dependency
at `bridges/idris2` there. The workflow names `LANGUAGE_BRIDGES_TOKEN`, but the
user received GitHub 404 for the configured repository. Public metadata and
repository searches did not establish a canonical replacement; this is not
proof that no such repository exists.

Do not create a token for the unresolved location. First establish the correct
owner/repository and whether the signed-in account can open it. If it is private,
obtain account access before configuring a least-privilege read credential.
If it was renamed or moved, update and pin the dependency to the verified source.
The public `hyperpolymath/nextgen-languages` repository is an index/coordinator,
not a confirmed replacement bridge source.
